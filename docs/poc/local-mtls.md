## 目的と対象

AC と RA 間の HTTPS 通信で使うクライアント証明書認証を理解するため、Python と OpenSSL で TLS/mTLS を小さく実装して検証する。

現在は、クライアントが CA 証明書を使ってサーバー証明書を検証する HTTPS までを実装している。サーバーがクライアント証明書を検証する mTLS は、次の検証段階となる。AWS 上の構成や本番の AC 接続仕様は、このローカル検証の対象に含めない。

実行方法は [local-mtls/README.md](../../local-mtls/README.md) を参照する。この文書には検証の目的、仕組み、結果を残す。

## 現在の構成

1. OpenSSL で検証用の自己署名ルート CA を作る。
2. サーバー用の秘密鍵と CSR（証明書署名要求）を作り、CA の秘密鍵で署名してサーバー証明書を発行する。
3. Python の HTTPS サーバーが、サーバー証明書と秘密鍵を読み込んで待ち受ける。
4. クライアントが信頼する CA 証明書を指定し、証明書の検証と TLS ハンドシェイクを経て HTTP GET を送る。

| ファイル | 役割 |
| --- | --- |
| `ca.crt` | クライアントがサーバー証明書を検証するための CA 証明書 |
| `ca.key` | サーバー証明書の署名に使う CA の秘密鍵 |
| `server.csr` | サーバー証明書の発行を求める署名要求 |
| `server.crt` | CA が署名したサーバー証明書 |
| `server.key` | TLS サーバーが使う秘密鍵 |

手動実行用のファイルは `local-mtls/certs/generated/` に生成する。生成物は Git 管理対象外とし、設定ファイルとスクリプトから作り直せるようにしている。テストでは一時ディレクトリに生成し、テスト終了後に削除する。

## コードと証明書設定の対応

- [server.py](../../local-mtls/mtls_poc/server.py) の `load_cert_chain` でサーバー証明書と秘密鍵を読み込み、`wrap_socket` で HTTP サーバーのソケットに TLS を追加する。
- [client.py](../../local-mtls/mtls_poc/client.py) の `create_default_context(cafile=...)` で信頼する CA 証明書を指定する。証明書検証と接続先のホスト名検証を有効にして接続する。
- [generate-certs.sh](../../local-mtls/scripts/generate-certs.sh) で CA とサーバー証明書を生成する。
- [server-ext.cnf](../../local-mtls/scripts/server-ext.cnf) は、署名時にサーバー証明書へ付ける X.509 拡張設定。`serverAuth` で用途を指定し、SAN に接続先の `localhost` と `127.0.0.1` を含める。鍵識別子も設定して、証明書チェーンの検証に使えるようにしている。

## 検証結果

2026-10-24 時点のローカル実行では、Python 3.13.17・pytest 9.1.1 で次の2件が成功した。

| ケース | 期待する結果 | 確認結果 |
| --- | --- | --- |
| サーバー証明書を発行した CA をクライアントが信頼する | HTTPS 接続が成立し、応答本文を取得できる | 成功 |
| 別の CA をクライアントが信頼する | サーバー証明書の検証に失敗する | `SSLCertVerificationError` を確認 |

[テストコード](../../local-mtls/tests/test_https.py) では、別々の CA を生成して信頼関係の違いを比較している。接続には `127.0.0.1` の一時ポートを使い、外部サーバーには接続しない。

この結果で確認できたのはサーバー証明書の検証までであり、クライアント証明書認証が成功したことを意味しない。また、ホスト名不一致や有効期限切れは個別のテストにしていない。

## 次に検証すること

- クライアント証明書を発行し、サーバー側で提示と検証を必須にする。
- 正常なクライアント証明書、証明書なし、信頼しない CA が発行した証明書をテストで比較する。
- 成功・失敗した理由を、Python の TLS 設定と OpenSSL の表示に対応づけて記録する。
